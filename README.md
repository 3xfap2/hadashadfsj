# Остаток

Система для ресторана: учёт продуктов по партиям со сроками годности, обработка заказов со списанием,
автоматический стоп-лист и рекомендации, какие блюда продавать в первую очередь.
Решение кейса «Мониторинг остатков, сроков годности и стоп-листов».

**Развёрнутая версия:** https://ostatok.onrender.com — кнопка «Открыть демо-ресторан» или вход под одной из демо-записей (см. «Запуск»).
Сервис на бесплатном тарифе: после простоя первое открытие занимает до минуты.

**Приложение для Android:** [ostatok.apk](https://github.com/3xfap2/hadashadfsj/releases/latest/download/ostatok.apk) — Android 8 и новее. Перед установкой разрешите установку из браузера;
если стояла предыдущая сборка, сначала удалите её.

### Интеграции

Внешние системы ходят в «Остаток» без входа сотрудника — по ключу в заголовке `X-Api-Key`. Ключи выдаёт управляющий: «Ресторан» → «Ключи внешних систем». У каждой системы свой ключ с названием и правами:

| Право | Что открывает |
|---|---|
| `supplies` | `POST /api/supplies/incoming` — входящая поставка (ждёт приёмки в кабинете) |
| `orders` | `GET /api/integration/menu` — меню, цены, стоп-лист; `POST /api/orders/external` — заказ |
| любое | `GET /api/integration/products` — названия и единицы продуктов (без цен и остатков) |

- Ключ показывается один раз, в базе хранится только SHA-256. Ресторан определяется ключом: ключ одного ресторана не видит данных другого.
- Нет ключа, он неверный или отозван — 401; у ключа нет нужного права — 403 с объяснением; больше 60 запросов в минуту с ключа — 429 с `Retry-After` (счётчик в памяти процесса).
- Отзыв ключа (`POST /api/restaurant/keys/{id}/revoke`) отключает только его. В открытом демо-ресторане ключ отзывается только в первые 30 минут после выдачи — ключ для показа посетители не отзовут.
- Ключ, выданный до появления прав, перенесён миграцией как «Ключ поставщика» с правом `supplies` и продолжает работать.

**Поставка извне.** На склад сразу не попадает: в кабинете появляется сигнал и карточка «Ждёт подтверждения» («Склад → Поставки»). Продукт — `productId` или точное название из справочника (`productName`), срок — `shelfLifeHours` или «годен до» (`expiresAt`). Срок партий считается от даты создания поставки (`createdAt`). Повтор с тем же `id` или номером — 409, дубля нет.

**Заказ извне.** Идёт через тот же `OrderService`, что и заказ официанта: годные партии блокируются, продукты списываются по FEFO одной транзакцией. 201 — принят и сразу на кухне (с пометкой источника); 409 — блюдо в стопе или не хватает продуктов, в ответе `unavailable` — что не приготовить, со склада ничего не списано. `id` — номер заказа во внешней системе: повтор с тем же номером от того же ключа возвращает прежний заказ. В журнале исполнитель — название ключа.

Страницы для показа: `/supplier/` — кабинет поставщика (справочник продуктов подтягивает по ключу), `/pos/` — касса / сайт кафе (меню со стоп-листом, корзина, заказ).

Примеры — для bash (Linux, macOS, Git Bash). В Windows PowerShell вызывайте `curl.exe`, а не `curl`, и экранируйте кавычки в JSON.

```bash
# Поставка → 202, ждёт подтверждения в кабинете
curl -X POST https://ostatok.onrender.com/api/supplies/incoming -H "X-Api-Key: ost_…" -H "Content-Type: application/json" \
  -d '{"number":"ВН-1001","supplier":"Фермерский двор","supplierInn":"7701234567","items":[{"productName":"Томаты","quantity":5}]}'

# Меню со стоп-листом и заказ на доставку → 201 или 409
curl https://ostatok.onrender.com/api/integration/menu -H "X-Api-Key: ost_…"
curl -X POST https://ostatok.onrender.com/api/orders/external -H "X-Api-Key: ost_…" -H "Content-Type: application/json" \
  -d '{"id":"SITE-1001","delivery":true,"items":[{"dishId":"<dishId из меню>","quantity":2}]}'
```

Сотрудник склада может прислать входящую поставку и по своему входу (кабинет, бот); поставку, которую он вводит сам, подтверждать не нужно: `POST /api/supplies`.

### Печать журнала движений

Журнал движений (поставки, продажи, списания, заготовки, инвентаризация) запечатан хэш-цепочкой. Запись движений не изменилась: печать — отдельная фоновая задача (`JournalSealer`), которая раз в 30 секунд берёт ещё не запечатанные движения ресторана по возрастанию `Id` и даёт каждому номер в цепочке (`SealNo`), `Hash = SHA-256(хеш предыдущей записи + неизменяемые поля движения)` и время печати (`SealedAt`). Порядок цепочки — номер печати, а не `Id`: транзакция, начатая раньше, может закончиться позже соседних.

`GET /api/stock/journal/verify` (управляющему) пересчитывает цепочку с первой записи: «цела, запечатано N, последний хеш …» или номер первой записи, где хеш не сошёлся (запись изменили) или пропущен номер (запись удалили). На экране «Склад → Журнал» — плашка с итогом и кнопкой «Проверить».

Честно о границах: печать защищает от незаметной правки журнала в базе — исправленное количество или удалённая строка видны сразу. От администратора базы, который перепишет записи и пересчитает все хеши после них, она не защищает. Следующий шаг — регулярно выгружать последний хеш во внешнее хранилище (письмо владельцу, другой сервер) и сверять с ним.

### Одновременные заказы

Заказ выполняется одной транзакцией (`Features/OrderService.cs`):

1. `UPDATE "Restaurants" SET "LastOrderNumber" = … RETURNING` выдаёт номер заказа и блокирует строку ресторана до конца
   транзакции: заказы одного ресторана идут строго по очереди, номера — подряд без дыр, разные рестораны друг другу не мешают.
2. Повтор по `Id` от клиента возвращает уже созданный заказ, ничего не списывая.
3. Перепроверяется ручной стоп (`FOR SHARE` по блюдам): повар мог снять блюдо, пока заказ оформлялся.
4. Годные партии блокируются `SELECT … FOR UPDATE` в едином порядке (`ExpiresAt, Id`) — от тех, кто очередь ресторана
   не берёт: ручного списания и автосписания.
5. `Fefo.Allocate`, движения в журнал, коммит. Ожидание любой блокировки — не дольше 5 с (`lock_timeout`), дальше ответ 409 «повторите».

Это проверяют тесты `Параллельные_заказы_не_списывают_больше_чем_есть` (запас на 5 порций, 20 заказов одновременно —
принято ровно 5) и `Заказ_одновременно_с_ручным_списанием_той_же_партии_не_уводит_её_в_минус`.

### Зал и брони

Раздел «Зал» (`/app/hall`): схема столов по зонам, брони, посадка, уборка и журнал. Работают управляющий, шеф и официант;
схему, правила броней и закрытие столов меняет только управляющий (`Access.Hall`, `Access.HallAdmin`).

- **Модель.** Столик, бронь и визит — отдельные записи (`HallTable`, `Reservation`, `Visit`, плюс `TableBlock`, `HallSettings`, журнал `HallEvent`).
  Состояние стола не хранится, а вычисляется на момент среза: «недоступен» (блокировка) → «занят» (незавершённый визит) →
  «уборка» (гости ушли, готовность не подтверждена) → «бронь» (подтверждённая бронь начнётся в ближайшие 30 минут) → «свободен до …».
  Гости, засидевшиеся дольше ожидаемого, держат стол, пока визит не завершат; стол на уборке сам по таймеру не освобождается.
- **Правила.** Интервалы полуоткрытые, между гостями перерыв (по умолчанию 15 минут): бронь 18:00–20:00 допускает следующую с 20:15.
  Отмена и неявка освобождают интервал. Неявку можно отметить через 15 минут после начала. Перенос — одна транзакция:
  при конфликте бронь остаётся прежней. Нельзя уменьшить стол ниже будущей брони или убрать его в архив с бронями;
  закрыть стол с бронями можно только с явной отменой этих броней (иначе 409 со списком), поверх визита — нельзя.
- **Гонки.** Каждая команда, меняющая занятость стола, блокирует строку стола (`SELECT … FOR UPDATE`) до конца транзакции,
  проверка пересечений идёт уже под блокировкой. Последний рубеж — уникальные индексы: один незавершённый визит на стол,
  один визит на бронь. Ограничение исключения на `tstzrange` (`btree_gist`) не используется: перерыв настраивается, и его пришлось
  бы хранить в самой записи. Повтор запроса (двойное нажатие) — идемпотентность по `id` от клиента, как у заказа.
- **Время.** Хранятся абсолютные метки (UTC); дата и часы в запросах и на экране — по часам ресторана. Часовой пояс пока один
  на сервер: `Stock:UtcOffsetHours` (по умолчанию +3). Бронь 23:00 на 2,5 часа заканчивается в 01:30 следующего дня и видна в обоих днях.
- **Заказы.** Номер стола схемы — место заказа «Стол N»: официант выбирает стол из схемы, у занятого стола в карточке видны его
  открытые заказы. Ресторан без схемы работает как раньше (столы по числу из настроек). Завершение визита оплату не проводит.
- **API.** `GET /api/hall?date=&time=` — срез зала; `GET /api/hall/reservations?date=&q=&status=`; `GET /api/hall/options` — подбор стола
  с причиной недоступности; `POST /api/hall/reservations`, `PUT …/{id}` (с `version`), `POST …/{id}/cancel|no-show|seat`;
  `POST /api/hall/tables/{id}/seat|ready|block`, `POST /api/hall/visits/{id}/finish|extend`, `POST /api/hall/blocks/{id}/lift`;
  схема и настройки — `/api/hall/zones`, `/api/hall/tables`, `/api/hall/settings`; журнал — `GET /api/hall/journal`. Конфликт занятости — 409 с причиной.
- **Не сделано в первом этапе:** объединение столов, депозиты, лист ожидания, онлайн-бронирование гостем, сообщения гостям, часовой пояс на ресторан.

### Кэш стоп-листа и горячих предложений

- **Что:** `GET /api/stop-list`, `/api/hot-offers`, `/api/hot-offers/plan`, `/api/stock` — их перечитывает каждый терминал официанта и каждый открытый экран (`Features/ReadCache.cs`).
- **Ключ:** ресторан + версия данных ресторана + адрес + видит ли роль закупочные цены (официант и шеф получают разные записи).
- **Сброс:** версия растёт после каждого зафиксированного изменения данных ресторана — в момент коммита транзакции (`PublishChanges` → `EventBus.Publish`, тот же сигнал, что уходит экранам по SSE); фоновое автосписание сбрасывает кэш всех ресторанов. Версия читается до похода в базу, поэтому ответ, посчитанный во время коммита, ляжет под старой версией и не будет прочитан.
- **Время:** партия истекает без записи в базу, поэтому запись живёт до срока ближайшей годной партии, но не дольше 15 секунд (часы до конца срока и прогноз стопа сдвигаются за это время незаметно).
- **Стадо:** одинаковые запросы после сброса ждут один расчёт (`Lazy<Task>` на ключ). Ответ несёт `ETag`, на `If-None-Match` — 304; заголовок `X-Cache: hit|miss`, счётчики попаданий и промахов — в `GET /health`.
- **Продажа не зависит от кэша:** заказ и списание читают партии из базы под `FOR UPDATE`, кэш только показывает.
- **Почему память процесса, а не Redis:** сервер один, делить кэш не с кем, а пересчёт (четыре запроса с группировкой) быстрее похода в сеть; после перезапуска кэш заполняется первым же запросом. При нескольких экземплярах — Redis и рассылка сброса через pub/sub или `LISTEN/NOTIFY` PostgreSQL.

### Алгоритм горячих предложений

Приоритет блюда — сумма вкладов его ингредиентов, у которых срок истекает в пределах горизонта (48 часов):

```
вклад = Σ по истекающим партиям (количество, которое блюдо успеет израсходовать × цена × срочность) ÷ √N
срочность = 1 − часов до конца срока ÷ горизонт
N = число блюд в продаже с этим продуктом
```

Горизонт, вес срочности (степень: срочность ^ (вес ÷ 50)), деление на √N и потолок скидки настраиваются в кабинете.

Количество ограничено остатком партии и числом порций, на которое хватает остальных ингредиентов.
Блюда в стоп-листе не предлагаются. Каждая запись сбрасывает кэш ресторана, поэтому после заказа,
поставки или списания список сразу меняется.

Управляющий правит список вручную: закрепляет блюдо первым, скрывает его или добавляет своё блюдо с причиной
(«повар Иван сегодня готовит фирменное»). Добавленное блюдо официант видит с пометкой «добавлено управляющим»;
в план спасения и суммы оно не входит, блюдо в стопе не показывается.

(поставки, заказы, отказы, списания, часы в стопе), посчитанная теми же правилами, что и рабочие операции (`Data/DemoHistory.cs`).
Если в демо-ресторане 48 часов не было поставок, при запуске сервера склад пополняется теми же поставками
со сроками от текущего момента, чтобы меню не стояло целиком в стопе (`Data/DemoSeed.cs`).
Вход в кабинет: кнопка «Открыть демо-ресторан» или одна из демо-записей с паролем `demo2026`:
`demo` (шеф-повар), `manager` (управляющий), `cook` (повар), `storekeeper` (кладовщик), `waiter` (официант).
Заказы оформляет только официант.
Заявки и вопросы с лендинга видит только закрытая запись `support`: её пароль задаётся переменной `Auth__SupportPassword`
(локально — `support-local-2026` из настроек разработки), открытым демо-записям этот раздел недоступен.
Описание API: http://localhost:5078/openapi/v1.json.

Ключ подписи и пароль базы в `appsettings.Development.json` — только для локального запуска.
На сервере ключ задаётся переменной окружения `Auth__Key`, строка подключения — `ConnectionStrings__Db`.

## Размещение на сервере

`Dockerfile` в корне собирает один образ: сайт кладётся рядом с API, и сервер отдаёт его сам. Переменные окружения:

| Переменная | Значение |
|---|---|
| `ConnectionStrings__Db` | адрес базы: строка Npgsql или `postgres://…` от хостинга |
| `Auth__Key` | секрет подписи токенов, не короче 32 символов |
| `Auth__SupportPassword` | пароль закрытой записи `support` |
| `Proxy__TrustForwardedHeaders` | `true`, если перед сервером стоит прокси хостинга |
| `Seed__Demo` | `true`, чтобы наполнить демо-ресторан |
| `Telegram__BotToken` | токен бота поддержки; без него бот выключен |

Проверка работоспособности: `GET /health` (без базы, для пингера) и `GET /health/ready` (с запросом к базе), см. «Наблюдаемость».

## Наблюдаемость

- **`GET /health`** — мгновенно и без базы: им пользуется пингер, который не даёт бесплатному хостингу усыпить сервер.
  Отдаёт `status`, `version` — коммит, из которого собран сервер (`RENDER_GIT_COMMIT` задаёт Render; при своей сборке — `docker build --build-arg GIT_SHA=$(git rev-parse HEAD)`; иначе `local`), `startedAt` — время запуска, и счётчики кэша чтений (`cache`: попадания, промахи, сбросы).
- **`GET /health/ready`** — с запросом `SELECT 1` к базе (не дольше 3 секунд): `200 {"status":"ready"}` или `503 {"status":"unavailable"}`. Для проверки готовности при выкладке и для мониторинга.
- **Номер запроса:** каждый ответ несёт `X-Request-Id`. Если клиент или прокси прислал свой (до 64 символов: буквы, цифры, `-_.:`), используется он, иначе создаётся новый. Номер попадает в область журнала (`XRequestId`) — по нему находятся все строки одного запроса, в том числе ответ 500.
- **Журнал на сервере — JSON**, по записи на строку, с областями (`AddJsonConsole`): хостинг или сборщик логов разбирает поля без регулярных выражений. В конце каждого запроса — строка «метод, адрес, код, время в мс». В режиме разработки журнал обычным текстом.

```json
{"Timestamp":"2026-10-15T14:38:59.979Z","LogLevel":"Information","Category":"Ostatok.Requests","Message":"GET /health/ready → 200 за 28 мс",
 "State":{"Method":"GET","Path":"/health/ready","Status":200,"Elapsed":27.86},"Scopes":[…,{"XRequestId":"b284f94b25ee4437a19242404ff16a8c"}]}
```

## Нагрузка

> Замер на домашнем компьютере (Intel i3-12100F, 4 ядра / 8 потоков, Windows 10), Docker Desktop, одна копия сервера и своя база PostgreSQL в контейнере;
> нагрузку подаёт та же машина. Данные — демо-ресторан. Это порядок величин, а не обещание для боевого сервера: на бесплатном тарифе Render ресурсов меньше.

| Сценарий | Нагрузка | Результат | p50 | p95 |
|---|---|---|---|---|
| `GET /api/stop-list`, кэш включён | 20 клиентов без пауз, 30 с | **2 724 RPS**, 0 ошибок; промахов кэша 3 на 87 680 запросов | 6,3 мс | 13,6 мс |
| `GET /api/stop-list`, кэш выключен (`Cache__Enabled=false`) | то же, те же данные | **598 RPS**, 0 ошибок; каждый запрос считается по базе | 29,6 мс | 59,6 мс |
| 50 одновременных заказов на последние 5 порций, 3 раунда | 50 запросов разом | в каждом раунде **ровно 5 × 201 и 45 × 409**, списано 1,000 кг из 1, остаток 0, в минус не ушёл | 196–580 мс | 305–814 мс |
| Смешанная, 60 с: официанты | 20 заказов в секунду | 1 200 заказов, все 201, **5xx — 0** | 12,5 мс | 21,2 мс |
| — терминалы | 10 чтений стоп-листа в секунду | 600 × 200 | 7,7 мс | 12,4 мс |
| — кладовщик | поставка извне + приёмка раз в 2 с | 30 × 202 и 30 × 200 | 20,6 мс | 28,6 мс |

- Кэш чтений даёт ×4,6 по пропускной способности стоп-листа и в 4–5 раз меньшую задержку; стоп-лист при этом не отстаёт от базы (сброс при каждой записи, см. «Кэш стоп-листа»).
- В гонке за последние порции задержка — это очередь на строке счётчика заказов ресторана: заказы проходят по одному, поэтому 50-й ждёт остальных. Первый раунд медленнее — сразу после запуска сервера.
- После смешанного прогона остатки всех пяти продуктов неотрицательны, поставки и приёмки не мешали заказам.

Сырые отчёты NBomber (md, csv, txt) и сводки прогонов — в `docs/load/`. Повторить:

```bash
# своя база и сервер (кэш выключается переменной -e Cache__Enabled=false)
docker run -d --name ostatok-load-db --network ostatok_default -e POSTGRES_USER=ostatok -e POSTGRES_PASSWORD=ostatok -e POSTGRES_DB=ostatok_load postgres:17-alpine
docker build -t ostatok:load .
docker run -d --name ostatok-load --network ostatok_default -p 127.0.0.1:8112:8080 -e "ConnectionStrings__Db=Host=ostatok-load-db;Database=ostatok_load;Username=ostatok;Password=ostatok" \
  -e Auth__Key=local-load-key-0123456789abcdef0123456789abcdef -e Seed__Demo=true ostatok:load
# из корня репозитория; сценарии: stop-list, race, mixed (без имён — все три)
dotnet run --project backend/tests/Ostatok.Load -c Release -- http://127.0.0.1:8112
```

Проект `backend/tests/Ostatok.Load` не входит в `Ostatok.slnx`, поэтому обычный `dotnet test` и CI его не запускают; адрес не из `127.0.0.1`/`localhost` он отвергает — боевой сайт нагрузкой не проверяется.
Сценарий «заказ одновременно с ручным списанием той же партии» проверяется обычным тестом (`PlatformTests`): 5 раундов, итог согласован, 5xx нет.

## Безопасность

- Все адреса API требуют токен, кроме входа, заявки и чата с лендинга (`/api/chats…`), меню для гостя (`/api/public/menu/{id}`),
  приёма поставки извне (`POST /api/supplies/incoming` — по ключу интеграции в `X-Api-Key`),
  фото блюд, описания API (`/openapi/v1.json`) и проверок работоспособности (`/health`, `/health/ready`).
- Права проверяет сервер по роли (`Features/Access.cs`): официант оформляет заказы, кладовщик — поставки и списания,
  повар — заготовки и ручной стоп; справочники и аналитика доступны шеф-повару и управляющему, сотрудники — управляющему.
- Данные ресторанов разделены: запрос видит только записи ресторана из токена (тест `Новый_ресторан_работает_в_своём_пространстве_и_не_видит_чужих_данных`).
- В журнале движения записано, кто провёл каждую операцию.
- После пяти неверных паролей подряд вход для логина закрывается на 10 минут. Кроме того, после 20 неверных попыток
  с любых адресов логин закрывается на 2 минуты (для открытых демо-записей этот общий счётчик не ведётся).
- Слабые пароли сотрудников (из списка частых, совпадающие с логином, из одного-двух символов) сервер отклоняет ответом 400.
- Пароли хранятся в виде хеша (PBKDF2 из ASP.NET Core Identity), восстановить пароль из базы нельзя.
- Личные данные посетителей лендинга — имена, контакты, переписка — лежат в базе зашифрованными (AES-256-GCM, `Data/PersonalData.cs`).
  Ключ задаётся переменной `Crypto__Key`; если её нет, выводится из `Auth__Key`.
- Токен перестаёт действовать сразу после удаления сотрудника, смены его роли или пароля, а не когда истечёт срок.
- Ответы API не кэшируются, запрещено встраивание во фреймы и подмена типа содержимого; вне режима разработки включён HSTS.
- Запросы к базе параметризованы; размер загружаемых файлов и частота запросов на вход, регистрацию и чат ограничены.
- Пять неверных попыток считаются по паре «логин + адрес»: чужие ошибки не закрывают вход сотруднику на 10 минут;
  общий счётчик на логин закрывает его лишь на 2 минуты и только при массовом подборе.
- Сервер не запустится вне режима разработки с ключом из настроек разработки; принимается только алгоритм подписи HS256.
- За обратным прокси включите `Proxy__TrustForwardedHeaders=true`, чтобы ограничения частоты считались по адресу клиента, а не прокси.
- Генератор событий выключается сам через 30 минут; база в `docker-compose.yml` слушает только локальный адрес.
- Роль из токена сверяется с базой; поток событий у каждого ресторана свой; ограничения базы (уникальность, внешние ключи,
  проверки количеств) продублированы понятными ответами 400 и 409.
- Трафик шифруется на уровне хостинга (HTTPS), диск базы — средствами провайдера базы данных.

## Telegram-бот для сотрудников

Отдельный процесс на Python (`bot/`), работает через то же API, что сайт и приложение: вход сотрудника, заказ,
поставка вручную и по фото накладной, списание и вскрытие партии, план спасения, уведомления о сроках и стоп-листе.
У бота 409 собственных тестов, они гоняются в CI вместе с тестами сервера; запуск и известные ограничения — в `bot/README.md`.
