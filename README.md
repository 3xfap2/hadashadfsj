# Остаток

Система для ресторана: учёт продуктов по партиям со сроками годности, обработка заказов со списанием,
автоматический стоп-лист и рекомендации, какие блюда продавать в первую очередь.
Решение кейса «Мониторинг остатков, сроков годности и стоп-листов».

## Что умеет

| Требование кейса | Как сделано | Где в коде |
|---|---|---|
| Приём поставок, партии со сроками | Поставка — документ с номером и несколькими продуктами; каждая позиция становится партией, срок = дата поставки + срок хранения из поставки или норматив продукта | `backend/src/Ostatok.Api/Features/SupplyEndpoints.cs` |
| Заказ, проверка ингредиентов, списание | Заказ из нескольких блюд списывает продукты из партий с самым ранним сроком; просроченные партии не используются | `Features/OrderService.cs`, `Domain/Fefo.cs` |
| Отказ при нехватке | Заказ не создаётся, ответ 409 перечисляет, какого продукта сколько нужно и сколько есть | `Features/OrderEndpoints.cs` |
| Автоматический стоп-лист | Считается при каждом запросе по техкартам и годным остаткам, с причиной: нет на складе, просрочено, не хватает на порцию | `Domain/Availability.cs` |
| Остатки по продуктам и партиям, оставшийся срок | Статус партии: годна, истекает за сутки, просрочена | `Features/StockEndpoints.cs` |
| Предложение необходимых поставок | По среднему расходу и срокам партий: что закончится раньше трёх суток и сколько заказать | `Domain/Forecast.cs` |
| Горячие предложения | Приоритет блюда по срокам его ингредиентов, с объяснением причины | `Domain/HotOffers.cs` |
| Автосписание просрочки | Фоновая задача списывает партии, просроченные дольше отсрочки | `Features/WriteOffService.cs` |
| Прогноз момента стопа | Когда блюдо уйдёт в стоп с учётом расхода и истечения партий | `Domain/Forecast.cs` |
| Аналитика | Списания по дням, продуктам и причинам; продукты, из-за которых отклоняются заказы | `Features/InsightsEndpoints.cs` |

### Одновременные заказы

Заказ выполняется одной транзакцией: годные партии нужных продуктов блокируются (`SELECT … FOR UPDATE`)
в едином порядке, поэтому два заказа не могут списать один и тот же остаток. Это проверяет тест
`Параллельные_заказы_не_списывают_больше_чем_есть`: запас на 5 порций, 20 заказов одновременно — принято ровно 5.

### Алгоритм горячих предложений

Приоритет блюда — сумма вкладов его ингредиентов, у которых срок истекает в пределах горизонта (48 часов):

```
вклад = Σ по истекающим партиям (количество, которое блюдо успеет израсходовать × цена × срочность) ÷ √N
срочность = 1 − часов до конца срока ÷ горизонт
N = число блюд в продаже с этим продуктом
```

Количество ограничено остатком партии и числом порций, на которое хватает остальных ингредиентов.
Блюда в стоп-листе не предлагаются. Список пересчитывается при каждом запросе, поэтому после заказа,
поставки или списания он сразу меняется.

## Устройство

- `backend/` — ASP.NET Core 10, EF Core, PostgreSQL. Расчёты лежат в `Domain/` и не зависят от базы.
- `web/` — React, TypeScript, SCSS. Лендинг с формой заявки и кабинет ресторана, адаптированы под телефон.
- `docker-compose.yml` — PostgreSQL для локального запуска.

## Запуск

Нужны .NET SDK 10, Node.js 20+ и Docker.

```bash
docker compose up -d                                  # PostgreSQL на порту 5433
cd backend
ASPNETCORE_ENVIRONMENT=Development dotnet run --project src/Ostatok.Api   # API на http://localhost:5078
cd ../web
npm install
npm run dev                                           # сайт на http://localhost:5173
```

При первом запуске API применяет миграции и наполняет базу демо-рестораном.
Вход в кабинет: `demo` / `demo2026` или кнопка «Открыть демо-ресторан».
Описание API: http://localhost:5078/openapi/v1.json.

Ключ подписи и пароль базы в `appsettings.Development.json` — только для локального запуска.
На сервере ключ задаётся переменной окружения `Auth__Key`, строка подключения — `ConnectionStrings__Db`.

## Тесты

```bash
cd backend
dotnet test    # нужен запущенный Docker: тесты поднимают PostgreSQL в контейнере
```

44 теста: расчёты (списание по срокам, стоп-лист, горячие предложения, прогноз, закупки) и сквозные
сценарии через HTTP на настоящем PostgreSQL.

## Безопасность

- Все адреса API, кроме входа, требуют токен.
- После пяти неверных паролей подряд вход для логина закрывается на 10 минут.
- Пароли хранятся в виде хеша.
